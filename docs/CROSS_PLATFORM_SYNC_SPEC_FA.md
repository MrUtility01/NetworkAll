# مشخصات همگام‌سازی مشترک ویندوز و اندروید

وضعیت این سند: قرارداد هدف و فهرست پذیرش؛ مواردی که آزمون نشده‌اند «تأییدنشده» محسوب می‌شوند.

## هدف محصول

- نسخهٔ ویندوز میزبان اختیاری سرور محلی باشد.
- نسخهٔ اندروید و رابط ویندوز از طریق IPv4/نام میزبان و TCP port به API متصل شوند.
- هر دو کلاینت در قطع شبکه، داده‌های محلی مجاز را نگه دارند و پس از اتصال مجدد همگام شوند.
- محتوای آموزشی مرجع از داده‌های شخصی (یادداشت، وظیفه، پیشرفت، پاسخ‌های آزمون و تنظیمات) جدا باشد.
- هیچ همگام‌سازی، seed یا ارتقای schema نباید بی‌هشدار اطلاعات کاربر را پاک کند.

## معماری هدف

- Server: Flask API + SQLite در مسیر دادهٔ محلی ویندوز.
- Android: Kotlin + Room + OkHttp/WorkManager.
- Windows client: رابط وب محلی و/یا کلاینت دسکتاپ، با همان قرارداد API.
- Network: فقط LAN خصوصی مورد اعتماد؛ اتصال پیش‌فرض loopback. برای دسترسی LAN، bind صریح، توکن تصادفی حداقل ۲۴ نویسه و قاعدهٔ Firewall محدود به پروفایل Private لازم است.
- HTTP ساده فقط برای آزمایش LAN مورد اعتماد است؛ برای شبکهٔ غیرقابل اعتماد باید HTTPS یا تونل امن اضافه شود. Port forwarding یا انتشار عمومی پشتیبانی نمی‌شود.

## دامنه‌های داده و مالکیت

1. Curriculum: شناسهٔ پایدار UID، نسخهٔ محتوا، hash و وضعیت تأیید علمی. انتشار محتوا از همگام‌سازی دادهٔ شخصی جدا باشد.
2. Study progress: وضعیت مطالعه، امتیاز/تلاش آزمون، مرور فاصله‌دار و زمان آخرین تغییر.
3. Tasks: UID، عنوان، توضیح، انجام‌شدن، موعد، اولویت، زمان یادآوری و tombstone حذف.
4. Notes: UID، عنوان، متن، برچسب‌ها، زمان تغییر و tombstone حذف.
5. Vault: اطلاعات رمزگذاری‌شدهٔ سمت کلاینت؛ سرور نباید به رمز آشکار نیاز داشته باشد. کلیدهای DPAPI/Android Keystore به‌صورت خودکار بین دستگاه‌ها قابل انتقال نیستند، پس انتقال Vault باید با طرح کلید مستقل و رضایت صریح انجام شود؛ تا آن زمان Vault خارج از sync عمومی بماند.
6. Planner/reminders: دادهٔ وظیفه می‌تواند همگام شود، اما اعلان‌ها روی هر دستگاه جداگانه زمان‌بندی می‌شوند.

## قرارداد پروتکل

- تمام درخواست‌ها schema version و device ID داشته باشند.
- احراز هویت با Authorization: Bearer token؛ توکن در URL، query string، log یا گزارش خطا قرار نگیرد.
- Manifest شامل UID، entity، revision/last_updated، content_hash و deleted باشد.
- Push/Pull صفحه‌بندی و محدودیت اندازه داشته باشد؛ payload بزرگ باید chunk شود.
- زمان‌ها در UTC با قالب ISO-8601 ذخیره شوند؛ نمایش محلی فقط در رابط انجام شود.
- UIDها پایدار و مستقل از شمارهٔ ردیف SQLite باشند.
- حذف با tombstone همگام شود، نه حذف فیزیکی فوری؛ پاک‌سازی tombstone فقط بعد از سیاست retention و تأیید همهٔ دستگاه‌های شناخته‌شده.
- timestamp به‌تنهایی برای حل تعارض کافی نیست: ساعت دستگاه‌ها ممکن است نادرست باشد. نسخهٔ افزایشی سمت سرور یا revision، hash و پاسخ صریح conflict لازم است.
- عملیات push باید idempotent باشد و retry شبکه رکورد تکراری نسازد.
- پاسخ API باید شمارش applied/unchanged/conflict/rejected و شناسهٔ تعارض‌ها را برگرداند.

## ایمنی داده

- قبل از migration یا import حجیم: backup با زمان، بررسی قابلیت بازیابی، dry-run و گزارش تغییرات.
- migration فقط additive/transactional باشد؛ حذف ستون/جدول نیازمند migration نسخه‌دار و مسیر حفظ داده است.
- هیچ fallback مخربی برای DB غیرخالی مجاز نیست.
- خطای decrypt در Vault هرگز مجوز حذف کلید یا بازنویسی رمز نیست.
- Sync باید آخرین زمان موفق را تنها پس از موفقیت کامل همهٔ مرحله‌ها ثبت کند.
- conflictها نباید بی‌صدا دور ریخته شوند؛ نسخهٔ سرور و کلاینت باید برای حل دستی قابل بازیابی بمانند.

## اولویت پیاده‌سازی

### P0 — اتصال قابل اعتماد
- تست health/hello از اندروید به IP ویندوز با توکن اشتباه و درست.
- نمایش خطای قابل فهم برای timeout، آدرس نامعتبر، 401، سرور ناامن و نسخهٔ پروتکل ناسازگار.
- تست Firewall/LAN و جلوگیری از bind ناامن.

### P1 — همگام‌سازی واقعی
- پیاده‌سازی end-to-end برای Tasks و Notes ابتدا؛ سپس Study progress.
- پیاده‌سازی tombstone، idempotency، conflict UI و retry.
- هر دو جهت Android → Server و Server → Android در تست‌ها اثبات شوند.
- Vault تا طراحی انتقال امن کلید در sync عمومی غیرفعال بماند.

### P2 — پایداری
- sync افزایشی، صفحه‌بندی، محدودیت payload، backup/restore و گزارش وضعیت.
- آزمون قطع شبکه وسط push/pull و اجرای مجدد.
- آزمون چند دستگاه و تغییر هم‌زمان یک UID.

### P3 — کیفیت محتوای آموزشی
- audit ساختاری تمام بسته‌ها و UIDها.
- قرنطینهٔ محتوای قالبی بدون حذف منبع.
- بازنویسی موضوعی هر درس ضعیف با هدف یادگیری، پیش‌نیاز، سازوکار، مثال حل‌شده، لابراتوار تکرارپذیر، خروجی مورد انتظار، عیب‌یابی، امنیت/rollback، سؤال و answer_key جدا، واژه‌نامه و منابع معتبر.
- ثبت سطح L0–L4 و source_status؛ «متن بلند» به‌تنهایی تأیید علمی محسوب نمی‌شود.
- اولویت بازبینی: درخت فصل‌ها، IP/subnetting، Ethernet/VLAN, switching/routing, TCP/UDP, DNS/DHCP, Windows/PowerShell, Linux, MikroTik, Cisco, firewall/VPN, monitoring/Zabbix, automation, Git.

## معیار پذیرش انتشار

- Build موفق اندروید و تست‌های Python.
- اتصال واقعی گوشی به سرور با IP خصوصی و توکن.
- round-trip برای هر entity فعال: ایجاد، ویرایش، حذف، قطع/وصل و تعارض.
- تست بازیابی backup و migration بدون از دست‌رفتن note/task/progress.
- درخت محتوا در دیتابیس خالی و دیتابیس قدیمی نمایش داده شود.
- گزارش audit بدون خطای schema/UID؛ تمام موارد علمی مشکوک یا اصلاح یا قرنطینه‌شده و فهرست آن‌ها قابل مشاهده باشد.
- نسخهٔ ویندوز و اندروید در README با مراحل نصب و عیب‌یابی قابل بازتولید مستند شوند.

## وضعیت شناخته‌شده در زمان تدوین

- شاخهٔ کاری فعلی APIهای اولیهٔ /api/sync/hello، /manifest، /pull و /push و کلاینت Android SyncClient را دارد.
- کلاینت Android فعلاً جریان اصلی sync را از LessonRepository اجرا می‌کند؛ همگام‌شدن کامل tasks/notes/planner و پیشرفت درسی بین دو دستگاه هنوز اثبات نشده است.
- پشتیبانی entity در endpoint به‌تنهایی اثبات نمی‌کند که ذخیره‌سازی و بازیابی آن entity در هر دو جهت پیاده‌سازی شده است.
- LAN روی HTTP با توکن، فقط برای شبکهٔ خصوصی مورد اعتماد است و جایگزین HTTPS در شبکهٔ غیرقابل اعتماد نیست.
- گزارش‌های audit خودکار ابزار غربالگری‌اند و جایگزین بازبینی علمی و اجرای واقعی لابراتوار نیستند.
