## ۱) چرا نام درس‌ها و دسته‌بندی در بعضی فصل‌ها مشخص نیست؟

### علت اصلی

| لایه | وضعیت | اثر روی UI |
|------|--------|------------|
| `lessons/base_curriculum.json` | اسکلت عنوان‌ها با پیشوند `[L0]` تا `[L4]` | نام‌ها تکراری و سطح‌محور دیده می‌شوند |
| `lessons/lessons.json` | در خیلی از فصل‌ها `items: []` (خالی) | متن غنی و نام تمیز افزوده وجود ندارد |
| `questions` / `answers` / `labs` | تقریباً همه فصل‌ها هنوز `0` رکورد canonical | بانک سوال/لاب در پوشه فصل خالی است |
| متن کامل درس | عمدتاً از runtime (`full_curriculum` / rich seed) می‌آید | در پوشه فصل فقط اسکلت دیده می‌شود |

**مثال نام‌گذاری اسکلت (فصل ۱):**

- زیرفصل: `۱.۱ پردازنده`
- درس‌ها: `[L0] CPU چیست... — آشنایی`، `[L1] ... — مقدماتی`، ... `[L4] ... — خبره`

این الگو برای ۵ سطح آموزشی عمدی است، ولی وقتی `lessons.json` خالی باشد، کاربر فقط همین عنوان‌های قالبی را می‌بیند و حس می‌کند «دسته‌بندی مشخص نیست».

### قانون فعلی محتوا

- **baseline** = اسکلت عناوین (همیشه در `base_curriculum.json`)
- **addon** = درس غنی با متن کامل در `lessons.json` (هنوز فقط بخشی از فصل‌ها)
- اپ ویندوز/اندروید از ترکیب baseline + addon + seed runtime درس می‌سازد؛ پوشهٔ فصل به‌تنهایی «نمایش نهایی UI» نیست.

## ۷) تعریف «فصل کامل» برای کار بعدی

یک فصل وقتی از نظر این ممیزی **کامل** محسوب می‌شود که:

1. `lessons/lessons.json` حداقل برای موضوعات اصلی رکورد با UID پایدار و متن کامل داشته باشد  
2. نام درس‌ها بدون وابستگی صرف به `[L0]…[L4]` خوانا باشد (یا در UI سطح جداگانه نمایش داده شود)  
3. `questions.json` و `answer_key.json` غیرخالی و هم‌تراز درس‌ها باشند  
4. `commands.json` و `examples.json` و `labs.json` حداقل برای مباحث عملی پر باشند  
5. `manifest.counts` با واقعیت فایل‌ها هم‌خوان باشد  
6. status از `base_from_runtime_source` / `review_required` به وضعیت پایدار برسد

### ساختار و منبع اصلی

- ساختار عددی `tools/chapters/1/` تا `tools/chapters/68/` در شاخهٔ `main` وجود دارد و برای هر فصل `manifest.json`، فایل‌های درس پایه/افزوده و بانک‌های دسته‌بندی‌شده تعریف شده‌اند.
- منبع اصلی قابل ویرایش هر فصل فقط فایل‌های مرجع داخل `tools/chapters/N/` است: `lessons/base_curriculum.json`، `lessons/lessons.json`، `questions/questions.json`، `answers/answer_key.json`، `examples/examples.json`، `commands/commands.json` و `labs/labs.json`.
- `build/chapter.json` خروجی تولیدی سازگاری است و نباید دستی ویرایش شود. فایل‌های `source_archive/`، `sources/`، بسته‌های قدیمی و محتوای runtime برای حفظ محتوا نگهداری می‌شوند، اما نباید بدون UID/قانون ادغام به‌عنوان رکورد دوم وارد UI شوند.
- `manifest.json` و `tools/chapters/INDEX_FA.md` شاخص شمارش‌اند؛ اعدادشان باید با بانک‌های JSON واقعی دوباره اعتبارسنجی شوند.
- در بعضی READMEهای فصلی هنوز مسیرهای قدیمی مانند `tools/chapters/ch09_...` به‌عنوان «مسیر اصلی» ذکر شده است. این ارجاع‌ها با ساختار عددی جدید ناسازگارند و باید در مرحلهٔ پاک‌سازی مستندات به مسیر عددی فصل و محل واقعی منبع اصلاح شوند؛ پوشه یا محتوای قدیمی را صرفاً به خاطر این ارجاع حذف نکنید.

### نتیجهٔ قابل اثبات از فایل‌های منبع فعلی

طبق `tools/chapters/INDEX_FA.md` در شاخهٔ `main`:

- ۶۸ فصل فهرست شده‌اند؛ ساختار پوشه‌ای موجود است.
- ۱۷ فصل دارای درس افزودهٔ غیرصفر و ۵۱ فصل دارای `addon_lessons = 0) هستند.
- فصل‌های بدون درس افزوده: `1–6, 8–12, 15–19, 22–27, 33–34, 36–50, 52–59, 61–64`.
- فصل‌های دارای افزوده، الزاماً «کامل» نیستند. فصل‌های 21، 60، 66 و 67 به‌خصوص نسبت به دامنهٔ موضوعی خود کم‌عمق‌اند؛ فصل 68 حجیم است اما نیازمند کنترل هم‌ترازی رکوردها و پاسخ‌هاست.
- نمونهٔ بررسی مستقیم: `tools/chapters/8/lessons/lessons.json` در `main` دارای `items: []) است؛ پس غنی‌سازی فصل ۸ در منبع canonical هنوز ثبت نشده است. همچنین `tools/chapters/1/manifest.json` مقدار `addon_lessons: 0) و همهٔ بانک‌های دسته‌بندی را صفر گزارش می‌کند.
- شمار دقیق سؤال/پاسخ/لاب و درس‌های کم‌عمق در SQLite **نامشخص** است تا فایل واقعی دیتابیس در اختیار ممیزی قرار گیرد. شمارهای manifest صرفاً ادعای فایل منبع‌اند، نه اثبات محتوای درج‌شده در دیتابیس.

### آزمون و بسته‌بندی Windows/Android

Workflow مخزن `.github/workflows/build-platforms.yml` برای شاخهٔ `main` با push اجرا می‌شود. در آن:
1. Android: بازتولید بسته‌ها، بررسی وجود فصل‌های ۱ تا ۶۸، بررسی UID تکراری و وجود محتوای کامل، سپس `assembleDebug` و انتشار APK به‌عنوان artifact.
2. Windows: کامپایل پایتون، ساخت ZIP کامل منابع و تست یکپارچگی ZIP و حضور فایل‌های کلیدی.

این‌ها تست‌های CI و ساخت بسته هستند؛ جایگزین اجرای دستی برنامه روی دستگاه Android یا Windows واقعی نیستند. نتیجهٔ اجرا باید پس از پایان GitHub Actions با وضعیت واقعی هر job تکمیل شود؛ تا پیش از مشاهدهٔ run موفق، وضعیت را «قبول‌شده» اعلام نکنید.

### اقدام‌های باقی‌مانده و معیار پایان

1. دریافت `server/data/encyclopedia.db` و اجرای `python tools/audit_content.py --db server/data/encyclopedia.db --json reports/content_audit.json` برای شمارش واقعی فصل‌ها، درس‌ها، طول متن‌ها، سناریوها و موارد کم‌عمق.
2. تولید گزارش تکراری‌ها با UID و هش محتوا؛ ادغام فقط پس از تعیین منبع canonical و حفظ تمام نسخه‌های اصلی در آرشیو.
3. غنی‌سازی مرحله‌ای فصل‌های دارای `items: [])، شروع با فصل‌های حیاتی 8 و 24 و سپس 1–6، 9–12، 15–19 و سایر فصل‌های فهرست‌شده؛ هر بسته باید متن کامل، سؤال، پاسخ‌نامهٔ هم‌UID، مثال، فرمان/لاب مرتبط و اعتبارسنجی JSON داشته باشد.
4. اجرای `python scripts/assemble_chapter_packs.py --strict`، تست‌های CI، و ثبت لینک run و artifact واقعی Windows/Android در همین سند.
5. فقط پس از بررسی دیتابیس، CI و اجرای واقعی برنامه می‌توان وضعیت را از `review_required` به تأییدشده تغییر داد.

**وضعیت در تاریخ این بازبینی:** ساختار عددی در منبع عمومی حاضر است؛ ممیزی منبع نشان می‌دهد غنی‌سازی همهٔ فصل‌ها کامل نیست؛ ممیزی SQLite و نتیجهٔ نهایی build پس از تغییرات هنوز در این سند تأیید نشده‌اند.


### یافتهٔ مهم: اختلاف manifest و فایل‌های واقعی (تأیید مستقیم)

در بازبینی مستقیم فصل ۸، `manifest.json` مقادیر `questions=135`، `answers=135`، `examples=135`، `commands=135` و `labs=27` را اعلام می‌کند. فایل‌های بانک این دسته‌ها واقعاً رکورد دارند؛ در مقابل، `lessons/lessons.json` خالی است. بنابراین مسئلهٔ فصل ۸، خالی بودن درس‌های افزوده و احتمال تکراری/قالبی بودن محتوای دسته‌هاست، نه خالی بودن تمام بانک‌ها. شمار manifest باید با تعداد واقعی رکوردهای هر فایل مقایسه شود و کیفیت/تنوع متن‌ها هم ممیزی شود. این مورد به‌عنوان **نیاز به ممیزی کیفیت و تطبیق شمارها** ثبت می‌شود، نه مجوز حذف یا بازنویسی منبع‌های قدیمی.

### اصل حفظ محتوا

هیچ فایل یا بسته قدیمی برای کوچک‌کردن برنامه حذف نشده است. فایل‌های `build/chapter.json` خروجی تولیدی‌اند و باید با ابزارهای سازنده پروژه دوباره ساخته شوند؛ ویرایش دستی آن‌ها جایگزین فرایند build نیست.
