# دفترچهٔ آزمایشگاه فصل ۷ — مهندسی TCP

> وضعیت: طراحی‌شده؛ اجرای آزمایش روی دستگاه واقعی هنوز تأیید نشده است. همهٔ آزمایش‌ها را فقط روی میزبان‌ها و شبکه‌هایی اجرا کنید که مجوز دارید. از capture و log حاوی دادهٔ حساس محافظت کنید.

## هدف و معیار خروجی

این دفترچه مکمل درس‌های TCP است و یادگیرنده را از مشاهدهٔ socket تا تحلیل علت ریشه‌ای و اندازه‌گیری ظرفیت هدایت می‌کند. هر اجرا باید شامل محیط، نسخهٔ سیستم‌عامل و ابزار، IP/port، زمان، فرضیه، فرمان، خروجی خام، تفسیر، محدودیت‌ها و cleanup باشد. وجود یک علامت منفرد مانند timeout، retransmission یا RST برای اعلام علت قطعی کافی نیست.

## آزمایش ۱ — تشخیص listener و آدرس bind

### محیط
یک سرویس آزمایشی روی سیستم شخصی یا VM اجرا کنید. پورت را از قبل تعیین و مطمئن شوید با سرویس دیگری تداخل ندارد.

### ویندوز
```powershell
Get-NetTCPConnection -State Listen |
  Sort-Object LocalPort |
  Select-Object LocalAddress, LocalPort, OwningProcess
```

برای PID مشخص:
```powershell
Get-Process -Id <PID>
```

### لینوکس
```bash
ss -lntp
ss -tan state established
```

### تفسیر
- `127.0.0.1` فقط loopback همان میزبان است؛ این آدرس برای کلاینت LAN قابل استفاده به‌عنوان آدرس سرور نیست.
- `0.0.0.0` در IPv4 معمولاً به معنی گوش‌دادن روی همهٔ آدرس‌های IPv4 محلی است؛ این انتخاب باید با firewall و مدل تهدید سازگار باشد.
- `LISTEN` فقط وجود socket شنونده را نشان می‌دهد، نه سلامت منطق برنامه، TLS یا ذخیره‌سازی داده.
- PID را با سرویس مورد انتظار تطبیق دهید؛ پورت صحیح به‌تنهایی هویت فرایند را ثابت نمی‌کند.

### معیار قبولی
IP و پورت محلی، PID و سرویس مالک socket مستند شده‌اند. اگر اتصال از میزبان دیگر لازم است، bind روی رابط خصوصی و محدودسازی firewall به‌صورت جداگانه تأیید شده است.

## آزمایش ۲ — جداسازی TCP از برنامه

از کلاینت ویندوز:
```powershell
Test-NetConnection <server-ip> -Port <port> -InformationLevel Detailed
```

از لینوکس در صورت نصب ابزار:
```bash
nc -vz <server-ip> <port>
```

این آزمون فقط دسترسی TCP به مقصد و پورت را بررسی می‌کند. برای سرویس HTTP، بعد از آن درخواست کاربردی را با ابزار مناسب و دادهٔ غیرحساس ارسال کنید. موفقیت TCP، موفقیت TLS، احراز هویت، مجوز، parse شدن درخواست یا پایدارسازی عملیات را تضمین نمی‌کند.

### شاخه‌های عیب‌یابی
1. **Listener وجود ندارد:** سرویس، پورت پیکربندی و خطای startup را بررسی کنید.
2. **Listener فقط روی loopback است:** مشکل bind را حل کنید؛ باز کردن firewall به‌تنهایی کافی نیست.
3. **SYN از کلاینت خارج می‌شود اما به سرور نمی‌رسد:** IP مقصد، VLAN، route، ACL و محل capture را بررسی کنید.
4. **SYN به سرور می‌رسد اما SYN-ACK برنمی‌گردد:** listener، bind، firewall میزبان و مسیر برگشت را بررسی کنید.
5. **Handshake کامل است اما برنامه پاسخ نمی‌دهد:** لاگ برنامه، deadline، پردازش درخواست و پروتکل کاربردی را بررسی کنید.
6. **پاسخ HTTP خطا دارد:** لایهٔ برنامه پاسخ داده است؛ علت را از status code، لاگ و قرارداد API بررسی کنید، نه از TCP به‌تنهایی.

## آزمایش ۳ — مشاهدهٔ handshake و teardown

در Wireshark از فیلتر نمایشی `tcp.port == <port>` استفاده کنید. فیلتر نمایشی را با capture filter اشتباه نگیرید: capture filter می‌تواند بسته‌ها را از ابتدا حذف کند. توالی معمول آغاز اتصال SYN، SYN-ACK و ACK است. پایان منظم می‌تواند FIN و ACK داشته باشد؛ RST نشان‌دهندهٔ reset است، اما مبدأ RST را از یک capture یک‌طرفه قطعی فرض نکنید.

برای هر رخداد tuple پنج‌تایی (مبدأ IP/port، مقصد IP/port و پروتکل)، زمان، flags، sequence/ACK و وضعیت socket را ثبت کنید. در صورت capture ناقص، شروع ضبط در میانهٔ اتصال یا offload سخت‌افزاری، نتیجه را محدود و صریح گزارش کنید.

## آزمایش ۴ — BDP و کنترل جریان/ازدحام

فرمول پایه:

`BDP (bit) = bandwidth (bit/s) × RTT (s)`

مثال: برای 100 Mbit/s و RTT برابر 80 ms:
- BDP = 100,000,000 × 0.08 = 8,000,000 bit
- بر حسب بایت: 1,000,000 byte، تقریباً 1 MB ده‌دهی

این عدد تخمین دادهٔ در پرواز برای مسیر ایده‌آل است، نه تضمین throughput و نه دستور افزایش بافر. rwnd محدودیت اعلام‌شده از سوی گیرنده است؛ cwnd محدودیت ارسال مبتنی بر کنترل ازدحام در فرستنده است. محدودیت برنامه، CPU، pacing، صف، loss و سربار TLS/VPN نیز مؤثرند.

### روش آزمایش
1. baseline را بدون تغییر ثبت کنید: RTT idle، RTT زیر بار، throughput، retransmission، CPU، حجم داده، تعداد جریان و مدت.
2. فقط یک متغیر را تغییر دهید؛ مثلاً RTT. نرخ لینک، حجم، تعداد جریان و نسخهٔ ابزار را ثابت نگه دارید.
3. چند تکرار انجام دهید و ترتیب را تغییر دهید تا warm-up و بار پس‌زمینه نتیجه را منحرف نکند.
4. median و پراکندگی را گزارش کنید؛ بهترین اجرا را به‌تنهایی انتخاب نکنید.
5. تنظیمات آزمایشی را پاک کنید و بازگشت به baseline را مستقلاً بررسی کنید.

## آزمایش ۵ — RCA قطع اتصال

برای رخداد «پس از چند دقیقه سکوت اتصال قطع می‌شود»، دست‌کم این فرضیه‌ها را جدا نگه دارید:
- idle timeout در تجهیز میانی؛
- deadline یا timeout در برنامه؛
- خاتمهٔ اتصال از سوی peer؛
- مسیر یک‌طرفه یا تغییر مسیر؛
- capture ناقص یا اختلاف ساعت.

یک timeline بسازید که زمان خطای کلاینت، لاگ سرور، socket state، capture دوطرفه و شمارنده‌های شبکه را کنار هم قرار دهد. اگر ساعت دو endpoint همگام نیست، اختلاف را تخمین بزنید و در گزارش ذکر کنید. اگر تغییر heartbeat مشکل را موقتاً رفع کرد، این به‌تنهایی محل timeout را اثبات نمی‌کند؛ ممکن است فقط اتصال را فعال نگه داشته باشد.

### شرط قبولی
برای هر فرضیه شاهد موافق، شاهد مخالف، آزمایش بعدی و شرط رد فرضیه ثبت شده است. «احتمالاً فایروال» نتیجهٔ قابل‌قبول RCA نیست مگر شواهد متمایزکننده ارائه شود.

## آزمایش ۶ — طراحی benchmark منصفانه

سؤال benchmark را دقیق بنویسید؛ مثلاً «تغییر RTT چه اثری بر throughput تک‌جریان دارد؟». نسخهٔ OS و ابزار، الگوریتم ازدحام، نرخ و جهت لینک، حجم داده، warm-up، مدت، تعداد جریان، CPU، RTT و روش اندازه‌گیری را ثبت کنید. نرخ مجموع چند جریان ممکن است بالاتر باشد، اما می‌تواند fairness را بدتر کند یا latency و مصرف منابع را پنهان سازد.

حداقل گزارش کنید:
- throughput و نرخ تکمیل عملیات؛
- p50/p95/p99 latency و timeout؛
- retransmission و RTT در حالت idle و زیر بار؛
- CPU، حافظه و تعداد اتصال؛
- دادهٔ خام هر تکرار، median، پراکندگی و محدودیت‌ها.

Capture میزبان الزاماً تصویر دقیق «روی سیم» نیست: TSO/GSO ممکن است segmentation را جابه‌جا نشان دهد، GRO/LRO می‌تواند segmentها را ادغام کند و checksum offload باعث checksum ظاهراً نامعتبر شود. محل capture، نسخهٔ OS/driver و وضعیت offload را ثبت کنید. تغییر offload یا تنظیمات TCP را فقط در محیط کنترل‌شده و با baseline و rollback انجام دهید.

## ایمنی، cleanup و حریم خصوصی

- از تست فشار، تزریق RST یا تغییر firewall روی شبکهٔ تولیدی خودداری کنید.
- قبل از تغییر تنظیمات، مقدار اولیه را ذخیره و شرط rollback را تعیین کنید.
- capture ممکن است token، cookie یا payload شخصی داشته باشد؛ دسترسی و زمان نگهداری را محدود کنید.
- فایل‌های آزمایشی و تنظیمات موقت را پس از پایان حذف یا بازگردانی کنید.
- یافتهٔ مستقیم، تفسیر محتمل و پیشنهاد نیازمند آزمون را در گزارش از هم جدا کنید.
