# دفترچهٔ لابراتوار پیشرفتهٔ MikroTik + Syslog + Zabbix
## NetworkAll — نسخهٔ فارسی

> وضعیت: طراحی‌شده و هنوز روی تجهیزات واقعی اجرا نشده است. تمام IPها و داده‌های نمونه در این سند آموزشی‌اند. پیش از استفاده، نسخهٔ RouterOS، سیستم‌عامل سرور و نسخهٔ Zabbix را ثبت و syntax و منوها را با مستندات همان نسخه تطبیق دهید.

## هدف و معماری مرجع

هدف این دفترچه رسیدن از «دستگاه ظاهراً قطع است» به تشخیص مبتنی بر شاهد است. معماری پیشنهادی:

- MikroTik ← نمونه‌برداری SNMP ← Zabbix Server/Proxy
- MikroTik ← Syslog روی UDP/514 ← rsyslog ← فایل تفکیک‌شده و logrotate
- در صورت نیاز، Agent یا collector دادهٔ فایل را به سامانهٔ پایش منتقل می‌کند.

SNMP و Syslog دو مسیر مستقل‌اند. SNMP معمولاً برای نمونه‌برداری دوره‌ای از وضعیت و counter است؛ Syslog رویدادها را منتقل می‌کند. سلامت یکی، سلامت دیگری را اثبات نمی‌کند. ممکن است polling کار کند ولی Firewall پیام‌های UDP/514 را حذف کند؛ یا Syslog دریافت شود ولی SNMP Timeout بدهد.

## ۱. قرارداد ایمنی قبل از تغییر

1. روی روتر تولیدی بدون پنجرهٔ تغییر و مسیر مدیریتی جایگزین آزمایش نکنید.
2. از پیکربندی نسخهٔ پشتیبان امن تهیه کنید. Export حاوی secret را در Git، تیکت عمومی یا screenshot قرار ندهید.
3. دسترسی مدیریتی جایگزین یا کنسول را آزمایش کنید؛ Rule مربوط به مدیریت را بدون راه بازگشت تغییر ندهید.
4. مقصد Syslog و Zabbix را با IP و مسیر برگشت معلوم انتخاب کنید. UDP/514 و UDP/161 را برای کل اینترنت باز نکنید.
5. هر تغییر باید فرضیه، baseline، معیار پذیرش، مهلت آزمون و rollback مشخص داشته باشد.
6. رخداد مصنوعی را در لابراتوار ایزوله بسازید؛ برای تولید هشدار، interface یا firewall شبکهٔ مشتری را قطع نکنید.

## ۲. موجودی و خط مبنا

| مورد | مقدار ثبت‌شدنی | علت |
|---|---|---|
| RouterOS | نسخهٔ دقیق | تفاوت syntax و قابلیت |
| Zabbix Server/Proxy | نسخهٔ دقیق | سازگاری Template و Trigger |
| IP روتر و سرور | آدرس واقعی در برگهٔ داخلی | شناسایی منبع و مقصد |
| Interface تحت پایش | نام و ifIndex | پیوند counter به رابط |
| Interval نمونه‌برداری | مقدار تنظیم‌شده | تأخیر کشف و بار polling |
| NTP و timezone | وضعیت هر سامانه | هم‌بستگی زمانی |
| مسیر برگشت | route و gateway | کشف ارتباط یک‌طرفه |
| نگهداری لاگ | روز و حجم تخمینی | ظرفیت دیسک |

برای مثال‌های مستندسازی از 192.0.2.0/24 استفاده کنید؛ این محدوده برای مستندات رزرو شده و نباید بدون برنامه‌ریزی به‌عنوان آدرس عملیاتی کپی شود.

## ۳. لابراتوار A — دریافت Syslog از ابتدا تا انتها

### مرحله A: بررسی روتر

ابتدا نسخه و تنظیمات فعلی را مشاهده کنید:

```routeros
/system logging action print detail
/system logging print detail
/system resource print
```

در Remote action باید مقصد، پورت، پروتکل پشتیبانی‌شده، قالب پیام و سیاست بافر روشن باشد. Ruleها را کمینه نگه دارید؛ ارسال دائمی همهٔ debug می‌تواند پهنای باند و دیسک را مصرف کند و دادهٔ حساس را افشا کند. Syntax تنظیم Remote Logging بین نسخه‌ها ممکن است تفاوت داشته باشد؛ دستور پیکربندی را از مستندات نسخهٔ نصب‌شده تطبیق دهید و ابتدا در لابراتوار آزمایش کنید.

### مرحله B: سه نقطهٔ دریافت در سرور

سه سؤال را مستقل پاسخ دهید: آیا بسته به کارت شبکه می‌رسد؟ آیا سرویس روی آدرس/پورت درست گوش می‌دهد؟ آیا پیام در فایل مقصد نوشته می‌شود؟

نمونهٔ بررسی Linux:

```bash
sudo ss -lunp
sudo tcpdump -ni any udp port 514
sudo journalctl -u rsyslog --since "10 minutes ago"
```

اگر packet دیده می‌شود ولی فایل تغییر نمی‌کند، listener، ruleهای rsyslog، مسیر فایل و مجوزها را بررسی کنید. اگر packet دیده نمی‌شود، IP مقصد، route، VLAN، ACL/Firewall و مسیر شبکهٔ مدیریت را بررسی کنید. UDP تأیید تحویل ذاتی ندارد؛ تنظیم‌شدن ارسال به معنی ثبت‌شدن پیام نیست.

### مرحله C: معیار پذیرش

یک پیام بی‌خطر با شناسهٔ یکتا بسازید. زمان تولید، packet capture، source IP/hostname، فایل مقصد و خط نهایی را ثبت کنید. تست زمانی Pass است که پیام یکتا در پنجرهٔ مورد انتظار در فایل درست ثبت شود و دسترسی فایل کمینه باشد. یک خط قدیمی در فایل، سلامت مسیر فعلی را ثابت نمی‌کند.

## ۴. تفکیک لاگ، چرخش و ظرفیت

برای هر نوع رویداد مسیر و دورهٔ نگهداری مشخص کنید. جداسازی فایل بر اساس میزبان یا facility جست‌وجو را آسان می‌کند. سیاست logrotate باید زمان یا اندازهٔ چرخش، تعداد نسخه‌ها، فشرده‌سازی، مالک/گروه فایل و رفتار سرویس هنگام reopen را تعیین کند. پس از تغییر، پیام تازه بفرستید و مطمئن شوید به فایل فعال رسیده است.

فرمول تخمین اولیه:

```
حجم روزانه ≈ بایت متوسط هر پیام × پیام در ثانیه × 86400
فضای خام ≈ حجم روزانه × روزهای نگهداری
```

مثال فرضی: 500 بایت × 4 پیام در ثانیه × 86400 ≈ 172.8 MB در روز، پیش از سربار و فشرده‌سازی. نرخ واقعی را اندازه بگیرید و burstها را در نظر بگیرید. آستانهٔ فضای آزاد و اقدام مسئول را تعریف کنید. پرشدن دیسک را فقط با حذف لاگ حل نکنید؛ افزایش نرخ پیام و سیاست retention را نیز بررسی کنید.

## ۵. SNMP و اصل کمترین دسترسی

در صورت پشتیبانی، SNMPv3 با احراز هویت و حریم خصوصی از community سادهٔ SNMPv1/v2c ترجیح دارد. از credential پیش‌فرض یا قابل حدس استفاده نکنید. دسترسی را به IP سرور/Proxy محدود کنید و فقط OIDهای لازم را بخوانید. Secretها نباید در مخزن کد، خروجی درس یا گزارش خطا ذخیره شوند. اگر دستگاه یا نسخه SNMPv3 را پشتیبانی نمی‌کند، محدودیت و ریسک راهکار جایگزین را ثبت و شبکهٔ مدیریت را ایزوله کنید.

در Zabbix، Host interface، نسخه و پارامترهای SNMP، credential، macro محرمانه، مجوز و دسترس‌پذیری UDP/161 را جدا بررسی کنید. Timeout به‌تنهایی علت را مشخص نمی‌کند: مسیر، ACL، credential، نسخه یا OID اشتباه همگی فرضیه‌اند. از یک OID شناخته‌شده و کم‌خطر شروع کنید؛ سپس به counterهای موردنیاز گسترش دهید.

## ۶. محاسبهٔ نرخ ترافیک و Reset شدن Counter

Counter بایت معمولاً تجمعی است. نرخ با اختلاف دو نمونه محاسبه می‌شود:

```
delta = counter_now - counter_previous
rate_bps = delta * 8 / elapsed_seconds
```

اگر counter از 12,000,000 به 12,600,000 بایت طی 60 ثانیه برسد، نرخ میانگین 80,000 bit/s است. این نتیجه فقط وقتی معتبر است که هر دو نمونه از همان interface و همان counter باشند، elapsed time درست باشد و counter reset یا wrap نکرده باشد.

اگر مقدار جدید کمتر از قبلی شد، نرخ منفی را ترافیک واقعی تفسیر نکنید. interface reinitialize، reboot، تغییر ifIndex، نوع counter یا wrap را بررسی کنید. برای رابط سریع، counter 64-bit در صورت پشتیبانی مناسب‌تر است. برای اثبات، مقدار خام، timestamp، uptime، ifIndex/نام رابط و سرعت لینک را کنار هم ثبت کنید.

## ۷. قرارداد Trigger و Recovery

هر هشدار باید سیگنال و واحد، پنجرهٔ زمانی، آستانهٔ دارای توجیه، سیاست دادهٔ کهنه، شرط Recovery، مالک، Runbook و آزمون مثبت/منفی داشته باشد. شرط عمومی «CPU بالاتر از 80%» بدون مدت، baseline و شناخت نوع تجهیز ممکن است هشدار کاذب بسازد. برای هشدار ظرفیت چند نمونهٔ پیوسته یا hysteresis ممکن است لازم باشد؛ برای رخداد امنیتی حساس تأخیر کمتر اهمیت دارد. شرط Recovery را مستقل طراحی کنید تا وضعیت نزدیک آستانه مرتب روشن و خاموش نشود.

هیچ expression یا کلید Item در این دفترچه به‌عنوان Template قابل Import تضمین نشده است. Syntax، preprocessing و macroها را در نسخهٔ دقیق Zabbix آزمایش کنید، Export واقعی بگیرید و Import مجدد را در یک Host آزمایشی بررسی کنید.

## ۸. ماتریس آزمون تکرارپذیر

| ID | آزمون کنترل‌شده | شواهد | معیار قبولی |
|---|---|---|---|
| T01 | پیام Syslog یکتا | packet + فایل مقصد | پیام در فایل درست ثبت شود |
| T02 | مسدودسازی موقت Rule در لابراتوار | capture و شمارندهٔ firewall | نقطهٔ افت مشخص شود |
| T03 | قطع دسترسی SNMP از Host آزمایشی | latest data و capture | stale از مقدار صفر تفکیک شود |
| T04 | کاهش counter در fixture مصنوعی | دو نمونه و timestamp | نرخ منفی نامعتبر تولید نشود |
| T05 | عبور مقدار از آستانه | history و event | Trigger در پنجرهٔ تعریف‌شده فعال شود |
| T06 | بازگشت به محدودهٔ عادی | history و recovery event | Recovery طبق شرط ثبت شود |
| T07 | افزایش لاگ فایل آزمایشی | disk usage و وضعیت logrotate | چرخش مطابق سیاست باشد |
| T08 | اختلاف زمان منبع آزمایشی | timestamp دو سامانه | خطر هم‌بستگی زمانی تشخیص داده شود |

T02 و T08 را فقط در شبکهٔ آزمایشگاهی اجرا کنید. زمان سیستم روتر تولیدی را برای تولید هشدار تغییر ندهید.

## ۹. درخت تصمیم RCA

**نشانه: داده یا هشدار در Zabbix دیده نمی‌شود.**

1. آیا latest data تازه است؟
   - هیچ Itemی تازه نیست: زمان آخرین دریافت، Server/Proxy، queue، شبکه و credential را بررسی کنید.
   - فقط یک Item مشکل دارد: key/OID، preprocessing و unsupported status را بررسی کنید.
2. آیا packet به سرور می‌رسد؟
   - خیر: IP مقصد، route، ACL، Firewall و VLAN را بررسی کنید.
   - بله: listener، نسخهٔ پروتکل، credential، rule پردازش و مسیر فایل را بررسی کنید.
3. آیا دادهٔ خام وجود دارد اما Trigger نیست؟
   - expression، نوع داده، واحد، پنجره، dependency و maintenance را بررسی کنید.
4. آیا Trigger رخ داده اما اعلان نرسیده؟
   - Action conditions، media، زمان‌بندی کاربر، severity و delivery log را بررسی کنید.

این درخت فرضیه‌ها را مرتب می‌کند؛ علت ریشه‌ای تنها پس از تطبیق دست‌کم دو شاهد مستقل ثبت شود. برای هر فرضیه مشخص کنید چه مشاهده‌ای آن را رد می‌کند تا عیب‌یابی به تأیید سوگیری‌دار تبدیل نشود.

## ۱۰. امنیت و حریم خصوصی

- UDP/514 و UDP/161 را فقط از مبدأهای لازم بپذیرید؛ در صورت امکان از روش انتقال امن و پشتیبانی‌شده استفاده کنید.
- رمز، community، کلید و token را در Git، screenshot، خروجی درس یا گزارش قرار ندهید.
- ساعت روتر و سرور را همگام کنید؛ زمان اشتباه ترتیب علت و معلول را مخدوش می‌کند.
- لاگ ممکن است IP کاربران یا ساختار شبکه را افشا کند؛ دسترسی خواندن و retention را کمینه کنید.
- نسخهٔ پیکربندی، شناسهٔ تغییر و نتیجهٔ rollback را ثبت کنید، نه secretها را.

## ۱۱. تغییر، Verification و Rollback

پیش از تغییر: backup امن، baseline، مسیر مدیریت جایگزین و معیار قبولی را ثبت کنید. پس از تغییر: پیام تازه، packet، فایل، تازه‌بودن Item، وضعیت Trigger، اعلان و فضای دیسک را بررسی کنید. مشاهدهٔ یک خط لاگ برای تأیید کل زنجیره کافی نیست.

Rollback: تغییرات آخر را طبق برنامه معکوس کنید، ruleهای موقت و Host آزمایشی را حذف کنید، پیکربندی Syslog را بررسی و سرویس را reload کنید؛ سپس پیام تازه بفرستید تا بازگشت سلامت اثبات شود. Backup را بدون بررسی نسخه و سازگاری مستقیماً روی دستگاه متفاوت Restore نکنید.

## ۱۲. قالب گزارش آزمون

برای هر تست ثبت کنید: شناسه و هدف؛ زمان و timezone؛ نسخه‌های RouterOS/Linux/Zabbix؛ توپولوژی؛ پیش‌شرط و baseline؛ گام‌های قابل تکرار؛ شواهد خام و محل ذخیره؛ نتیجهٔ مورد انتظار و واقعی؛ Pass/Fail/Blocked؛ اثر جانبی و rollback؛ بازبین و اقدام بعدی.

**قاعدهٔ انتشار:** تا وقتی تست با نسخهٔ ثبت‌شده اجرا نشده، وضعیت را designed_not_executed نگه دارید. دادهٔ ساختگی، مثال متنی و آزمون نحوی JSON به‌تنهایی موفقیت روی روتر واقعی را ثابت نمی‌کند.
