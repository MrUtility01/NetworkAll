# دفترچهٔ آزمایشگاه عمیق فصل ۸ — UDP و QUIC

> وضعیت: طراحی آزمایش؛ هنوز روی میزبان واقعی اجرا و تأیید نشده است. خروجی‌های نمونه در این سند **نمونهٔ توضیحی** هستند، نه خروجی ضبط‌شده از اجرای واقعی. آزمایش‌ها را فقط روی loopback یا میزبان‌هایی اجرا کنید که مجوز دارید.

## ۱. اهداف و نقشهٔ شایستگی

پس از این دفترچه باید بتوانید:

- تفاوت «تحویل دیتاگرام به سوکت»، «رسیدن بسته به رابط شبکه» و «پردازش موفق درخواست» را از هم جدا کنید.
- UDP را با شواهد سوکت، capture و لاگ برنامه عیب‌یابی کنید.
- اثر اندازهٔ payload، MTU، اتلاف و تأخیر را اندازه بگیرید و نتیجه را بدون تعمیم نادرست گزارش کنید.
- یک پروتکل کاربردی ساده را با شناسهٔ درخواست، timeout، محدودیت اندازه و سیاست تکرار امن طراحی کنید.
- QUIC را از «UDP خام» تشخیص دهید و بدانید که قابلیت اطمینان، رمزنگاری، کنترل ازدحام و جریان‌های چندگانه در QUIC در لایه‌های بالاتر پیاده می‌شوند.

### مدل ذهنی

UDP یک سرویس دیتاگرامی کم‌حالت است؛ نه تضمین تحویل می‌دهد، نه ترتیب، نه جلوگیری از تکرار و نه رمزنگاری. QUIC پروتکلی بالاتر از UDP است که قابلیت‌هایی مانند جریان‌های قابل‌اعتماد، بازیابی اتلاف، کنترل ازدحام و امنیت مبتنی بر TLS 1.3 را فراهم می‌کند. بنابراین گزارهٔ «QUIC همان UDP است» غلط است: QUIC از UDP به‌عنوان حامل استفاده می‌کند، اما رفتار انتقالی بسیار غنی‌تری دارد.

برای تحلیل رخداد، چهار نقطه را جدا ثبت کنید: (۱) برنامه ارسال را فراخوانی کرد، (۲) سیستم‌عامل دیتاگرام را پذیرفت، (۳) بسته در رابط شبکه مشاهده شد، (۴) برنامهٔ مقصد پیام را دریافت و پردازش کرد. مشاهدهٔ هر نقطه، نقطهٔ بعدی را اثبات نمی‌کند.

## ۲. آزمایش A — بررسی endpointهای UDP در ویندوز و Linux

### محیط و پیش‌نیاز
- Windows 10/11 با PowerShell، یا Linux با ابزار `ss`.
- دسترسی مدیریتی لازم نیست؛ ممکن است برای مشاهدهٔ برخی فرایندها دسترسی بیشتر لازم شود.
- قبل از تغییر فایروال، خروجی وضعیت پایه را ذخیره کنید. این آزمایش هیچ قاعده‌ای را تغییر نمی‌دهد.

### Windows
```powershell
Get-NetUDPEndpoint |
  Sort-Object LocalPort |
  Select-Object LocalAddress,LocalPort,OwningProcess
```

برای یک PID مشخص:
```powershell
$pidToInspect = 1234 # با PID واقعی جایگزین کنید
Get-Process -Id $pidToInspect
Get-NetUDPEndpoint |
  Where-Object OwningProcess -eq $pidToInspect
```

### Linux
```bash
ss -u -a -n -p
```

### تفسیر و معیار قبولی
- وجود endpoint ثابت می‌کند یک سوکت محلی در سیستم دیده شده؛ ثابت نمی‌کند بسته از شبکه می‌رسد.
- آدرس `127.0.0.1` یا `::1` فقط loopback است و از میزبان دیگر قابل‌دسترسی نیست.
- bind به `0.0.0.0` معمولاً به معنی گوش‌دادن روی همهٔ رابط‌های IPv4 محلی است؛ اما فایروال و مسیر هنوز می‌توانند دسترسی را مسدود کنند.
- برای IPv6، آدرس‌های wildcard و تنظیمات dual-stack را جدا بررسی کنید؛ رفتار IPv4-mapped در همهٔ برنامه‌ها یکسان نیست.

**قبولی:** نام فرایند، PID، آدرس bind و پورت را ثبت کنید و مشخص کنید کدام شواهد هنوز برای اثبات دریافت از راه شبکه لازم است.

## ۳. آزمایش B — ساخت فرستنده و گیرندهٔ UDP محلی با Python

این آزمایش از loopback استفاده می‌کند تا تفاوت دریافت محلی و دسترسی LAN را بیاموزید. فایل زیر را با نام `udp_lab.py` ذخیره کنید:

```python
import argparse
import socket
import time

parser = argparse.ArgumentParser()
parser.add_argument("mode", choices=["server", "client"])
parser.add_argument("--host", default="127.0.0.1")
parser.add_argument("--port", type=int, default=39001)
parser.add_argument("--count", type=int, default=5)
args = parser.parse_args()

if not 1 <= args.port <= 65535:
    raise SystemExit("port must be 1..65535")

if args.mode == "server":
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
        sock.bind((args.host, args.port))
        print(f"listening on {args.host}:{args.port}")
        for _ in range(args.count):
            data, peer = sock.recvfrom(2048)
            print(f"from={peer} bytes={len(data)} payload={data!r}")
else:
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
        sock.settimeout(1.5)
        for seq in range(args.count):
            payload = f"seq={seq} ts={time.time_ns()}".encode()
            sock.sendto(payload, (args.host, args.port))
            print(f"sent seq={seq} bytes={len(payload)}")
            time.sleep(0.2)
```

در ترمینال اول:
```bash
python udp_lab.py server --host 127.0.0.1 --port 39001 --count 5
```

در ترمینال دوم:
```bash
python udp_lab.py client --host 127.0.0.1 --port 39001 --count 5
```

### نتیجهٔ مورد انتظار
سرور باید پنج دیتاگرام دریافت کند و شمارنده‌های 0 تا 4 را در payload نشان دهد. این نتیجه فقط برای اجرای loopback و همین شرایط معتبر است؛ تضمین عمومی UDP نیست. در شبکهٔ واقعی ممکن است بسته گم یا خارج از ترتیب برسد.

### تمرین شکست
1. سرور را متوقف کنید و کلاینت را اجرا کنید. UDP ذاتاً خطای «connection refused» را به شکل قابل‌حمل و قطعی تضمین نمی‌کند؛ روی برخی سیستم‌ها ICMP خطا ممکن است به سوکت گزارش شود، اما برنامه نباید بر دریافت حتمی آن تکیه کند.
2. پورت کلاینت و سرور را عمداً متفاوت کنید. پیام ارسال‌شده به‌خودی‌خود اثبات دریافت نیست.
3. تعداد و اندازهٔ payload را ثبت کنید. برای جلوگیری از مصرف نامحدود منابع، در سرورهای واقعی محدودیت اندازه، نرخ، timeout و سیاست پردازش لازم است.

**پاک‌سازی:** پایان دادن به فرایند، بستن سوکت و حذف فایل آزمایشی در صورت عدم نیاز. این کد آموزشی است و بدون احراز هویت، مجوزدهی یا محدودسازی نرخ برای سرویس اینترنتی مناسب نیست.

## ۴. آزمایش C — مسیر‌یابی عیب‌یابی با packet capture

### پرسش اصلی
اگر کلاینت می‌گوید «ارسال موفق بود» اما سرور هیچ درخواستی ثبت نکرد، کدام فرضیه را ابتدا آزمایش می‌کنید؟

### جمع‌آوری شواهد
1. آدرس مقصد و پورت را از تنظیمات مؤثر برنامه ثبت کنید؛ به مقدار پیش‌فرض اکتفا نکنید.
2. روی رابط درست، capture بگیرید. در Wireshark از فیلتر `udp.port == 39001` استفاده کنید. در Linux، با مجوز مناسب:
   ```bash
   sudo tcpdump -ni any 'udp port 39001'
   ```
3. هم‌زمان لاگ برنامهٔ فرستنده و گیرنده را با timestamp جمع کنید.
4. آدرس مبدأ/مقصد، پورت، طول دیتاگرام و شمارندهٔ درخواست را با هم تطبیق دهید.

### درخت تصمیم
- **بسته در capture مبدأ نیست:** احتمالاً برنامه مسیر ارسال را اجرا نکرده، مقصد/پورت اشتباه است، خطا پیش از sendto رخ داده یا capture روی رابط نادرست است.
- **بسته در مبدأ هست، در مقصد نیست:** مسیر، VLAN، ACL، فایروال، NAT، رابط اشتباه یا شبکهٔ میانی را بررسی کنید. یک capture واحد برای تعیین محل دقیق drop کافی نیست.
- **بسته در مقصد دیده می‌شود، اما برنامه ثبت نمی‌کند:** bind address/port، namespace، socket اشتباه، اندازهٔ buffer، خطای parse، مجوزها و ازدحام receive queue را بررسی کنید.
- **برنامه دیتاگرام را دریافت می‌کند، اما پاسخ نمی‌رسد:** مسیر برگشت، bind سمت پاسخ، NAT state، فایروال و منطق برنامه را جدا آزمایش کنید.
- **پاسخ در مقصد کلاینت دیده می‌شود، اما UI خطا می‌دهد:** از شبکه به parser، timeout برنامه، شناسهٔ درخواست و state مدیریت‌شدهٔ رابط کاربر بروید.

هیچ‌گاه صرفاً با «پورت باز است» یا «ping جواب می‌دهد» نتیجه نگیرید که UDP برنامه سالم است. ICMP echo و UDP دو مسیر پروتکلی متفاوت‌اند.

## ۵. آزمایش D — MTU، اندازهٔ payload و fragmentation

MTU اندازهٔ حداکثر بستهٔ لایهٔ پیوندی است؛ سقف payload برنامه کوچک‌تر از MTU مسیر است، زیرا سربار IP، UDP و گاهی تونل‌ها/رمزنگاری نیز وجود دارد. اندازهٔ امن به مسیر، IPv4/IPv6، encapsulation و رفتار PMTUD وابسته است؛ یک عدد ثابت را برای تمام شبکه‌ها فرض نکنید.

### روش آزمایش
1. MTU رابط‌ها و وجود VPN/tunnel را ثبت کنید.
2. با payload کوچک شروع کنید و اندازه را در گام‌های کنترل‌شده افزایش دهید.
3. capture بگیرید و طول IP، fragmentation و پیام‌های ICMP مربوط به خطای MTU را بررسی کنید.
4. آزمایش را در IPv4 و IPv6 جدا انجام دهید؛ قواعد fragmentation این دو یکسان نیست.
5. نتیجه را در چند مسیر و با/بدون VPN مقایسه کنید.

### تحلیل
- fragmentation در مسیر می‌تواند باعث شود از دست رفتن یک fragment کل دیتاگرام را بی‌استفاده کند.
- فیلتر شدن ICMPهای لازم برای Path MTU Discovery ممکن است باعث black hole شود: بسته‌های کوچک کار می‌کنند ولی payloadهای بزرگ timeout می‌شوند.
- QUIC و برنامه‌های UDP باید اندازهٔ بسته و سازوکار PMTU را متناسب با مشخصات و پیاده‌سازی رعایت کنند؛ قطعه‌قطعه‌کردن دلخواه در لایهٔ برنامه نیز به framing و بازیابی نیاز دارد.

**معیار قبولی:** یک جدول از اندازهٔ payload، موفقیت/شکست، شواهد capture و مسیر شبکه بسازید. اگر علت را مستقیم مشاهده نکرده‌اید، آن را «فرضیه» ثبت کنید، نه نتیجهٔ قطعی.

## ۶. آزمایش E — طراحی قابلیت اطمینان در لایهٔ کاربرد

UDP به‌تنهایی delivery، ordering یا exactly-once را ارائه نمی‌کند. اگر پروتکل برنامه به آن‌ها نیاز دارد، طراحی باید صریح باشد.

حداقل فیلدهای پیشنهادی برای یک پروتکل آموزشی:
- `version`: نسخهٔ wire format.
- `request_id`: شناسهٔ یکتا برای هم‌بستگی درخواست و پاسخ.
- `sequence`: شمارنده برای تشخیص gap و reorder.
- `sent_at`: timestamp صرفاً برای اندازه‌گیری تقریبی؛ ساعت دو میزبان الزاماً همگام نیست.
- `payload_length`: طول مورد انتظار با سقف مشخص.
- `message_type`: نوع پیام که parser آن را allowlist می‌کند.

### سیاست timeout و retry
- timeout را بر اساس RTT مشاهده‌شده و نوع برنامه تنظیم کنید؛ مقدار بسیار کوتاه retryهای بی‌مورد می‌سازد و مقدار بسیار بلند UX را خراب می‌کند.
- retry را محدود و با exponential backoff و jitter انجام دهید تا چند کلاینت هم‌زمان بار انفجاری نسازند.
- برای عملیات تغییردهندهٔ وضعیت، `request_id` را در سمت سرور با نتیجهٔ قبلی نگه دارید تا retry همان عملیات را دوباره اجرا نکند.
- idempotency را با «exactly-once delivery» اشتباه نگیرید. شبکه می‌تواند پاسخ را گم کند؛ سرور شاید عملیات را انجام داده باشد. شناسهٔ یکتا و ثبت پایدار نتیجه، اثر تکرار را مدیریت می‌کند اما باید محدودهٔ زمانی و ذخیره‌سازی آن طراحی شود.
- پیام‌های دریافتی را از نظر طول، نوع، نسخه و نرخ اعتبارسنجی کنید. هیچ payload شبکه‌ای را قابل‌اعتماد فرض نکنید.

### آزمون‌های لازم
1. درخواست را یک بار بفرستید و نتیجه را بررسی کنید.
2. همان request_id را دوباره بفرستید؛ اثر جانبی نباید دوباره اجرا شود.
3. یک request_id جدید با payload متفاوت بفرستید؛ سرور نباید آن را به‌اشتباه تکرار قبلی فرض کند.
4. پاسخ را عمداً در محیط آزمایش حذف کنید و رفتار retry را ثبت کنید.
5. پیام خراب، طول بیش‌ازحد و نسخهٔ ناشناخته را رد کنید و مطمئن شوید فرایند از کار نمی‌افتد.

## ۷. QUIC؛ از مشاهده تا تصمیم معماری

QUIC صرفاً «UDP با رمزنگاری» نیست. QUIC انتقال جریان‌محور چندگانه و قابل‌اعتماد را همراه با بازیابی اتلاف و کنترل ازدحام فراهم می‌کند؛ TLS 1.3 برای handshake امنیتی آن به کار می‌رود. HTTP/3 پروتکل کاربردی جداگانه‌ای است که روی QUIC تعریف شده است.

### پرسش‌های تشخیصی
- آیا UDP در مسیر مسدود یا rate-limit شده است؟
- آیا handshake کامل می‌شود یا فقط بسته‌های ابتدایی دیده می‌شوند؟
- آیا خطا در TLS/گواهی، ALPN، نسخه، تنظیمات سرور یا شبکه است؟
- آیا packet capture به‌علت رمزنگاری، محتوای کاربردی را نشان نمی‌دهد؟ نبودن payload خوانا، به معنی نبودن ترافیک نیست.
- آیا مقایسهٔ TCP و QUIC با یک مقصد، حجم، مسیر، بار و تعداد تکرار یکسان انجام شده است؟

### روش benchmark
برای مقایسهٔ منصفانه، مقصد و شرایط شبکه را ثابت نگه دارید، cold-start و اتصال‌های گرم را جدا اندازه بگیرید، حداقل چندین تکرار انجام دهید و median و صدک ۹۵ تأخیر را گزارش کنید. throughput، زمان handshake، CPU، loss و نرخ خطا را نیز ثبت کنید. یک اجرای سریع یا یک تست speed-test، نتیجهٔ عمومی دربارهٔ برتری یک پروتکل اثبات نمی‌کند.

### ماتریس تصمیم
- TCP/TLS: گزینهٔ بالغ و سازگار با زیرساخت‌های موجود؛ برای stream معمولی انتخاب طبیعی بسیاری از سرویس‌هاست.
- UDP خام: مناسب وقتی برنامه واقعاً به دیتاگرام نیاز دارد و مسئولیت قابلیت اطمینان/امنیت/کنترل نرخ را آگاهانه می‌پذیرد.
- QUIC/HTTP/3: مناسب وقتی قابلیت‌های QUIC و سازگاری کتابخانه/زیرساخت نیاز پروژه را برآورده می‌کند؛ هزینهٔ عملیاتی، observability و محدودیت‌های شبکه باید سنجیده شود.

از ساخت رمزنگاری اختصاصی روی UDP خودداری کنید. برای کاربرد واقعی از پیاده‌سازی معتبر و به‌روز QUIC/TLS استفاده کنید و چرخهٔ به‌روزرسانی امنیتی را در نظر بگیرید.

## ۸. سناریوی capstone — «درخواست‌های پراکنده و تأخیر متناوب»

### علائم
کاربر گزارش می‌دهد برخی درخواست‌های UDP پاسخ نمی‌گیرند؛ پیام‌های کوچک معمولاً کار می‌کنند، پیام‌های بزرگ بیشتر timeout می‌شوند و پس از تغییر شبکه مشکل تغییر می‌کند.

### وظیفه
بدون تغییر تصادفی فایروال، فرضیه‌ها را با ترتیب شواهد بررسی کنید:
1. مقصد، پورت و interface واقعی را از برنامه استخراج کنید.
2. زمان ارسال و شناسهٔ درخواست را ثبت کنید.
3. capture هم‌زمان مبدأ و مقصد بگیرید.
4. طول payload و MTU مسیر را مقایسه کنید.
5. bind، receive buffer و parser را بررسی کنید.
6. در صورت نیاز، مسیر برگشت و NAT/firewall را با لاگ مجاز بررسی کنید.
7. فقط پس از مشاهدهٔ شواهد، یک تغییر کوچک پیشنهاد کنید و قبل از تغییر، وضعیت پایه و rollback را مستند کنید.

### معیار ارزیابی
- حداقل سه فرضیهٔ رقیب و شاهد لازم برای رد/قبول هرکدام.
- تمایز مشاهده از استنباط.
- یک بازتولید حداقلی و یک روش verification مستقل.
- ثبت ریسک و rollback.
- گزارش نهایی شامل root cause، شواهد، راه‌حل، اثر جانبی و پرسش‌های باز.

- **Datagram:** واحد مستقل پیام در UDP.
- **Socket:** نقطهٔ انتهایی ارتباطی در سیستم‌عامل.
- **MTU:** حداکثر اندازهٔ بستهٔ لایهٔ پیوندی روی یک رابط/مسیر مشخص.
- **PMTUD:** کشف MTU مسیر برای کاهش fragmentation یا شکست بسته‌های بزرگ.
- **Loss / Reordering / Duplication:** گم‌شدن، تغییر ترتیب و تکرار بسته.
- **RTT:** زمان رفت‌وبرگشت اندازه‌گیری‌شده.
- **Idempotency:** تکرار درخواست، اثر جانبی ناخواستهٔ جدید ایجاد نکند.
- **QUIC stream:** جریان منطقی درون اتصال QUIC؛ از یک دیتاگرام UDP یا یک اتصال TCP مستقل نیست.
- **HTTP/3:** HTTP روی QUIC؛ با خود QUIC یکی نیست.
